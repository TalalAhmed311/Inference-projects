Serving an open-source LLM with vLLM, end to end

This page covers the scripts in this folder, what vLLM does from the moment you run vllm serve until a token reaches the client, and how the benchmark measures it. The interactive parts are a code map, a request-path walkthrough, a continuous batching simulator and a GPU memory calculator.

03 · Deployment topology

Where everything runs

The server listens only on 127.0.0.1. Your laptop reaches it through an SSH tunnel, so port 8000 is never exposed to the internet. Run the benchmark on the instance so it can read nvidia-smi and network latency doesn't add to TTFT.

04 · Startup & GPU memory

What vllm serve does before the first request

  1. Parse configFlags, YAML, env vars and the model's config.json are combined into one VllmConfig.
  2. Download weights.safetensors files from the Hugging Face Hub are saved to ~/.cache/huggingface. Only the first run downloads them.
  3. Spawn processesThe API server and EngineCore run as separate processes and talk over ZMQ. There's one GPU worker per GPU.
  4. Load weights to GPUA 1.5B model in bf16 is about 3 GB; a 7B model is about 15 GB.
  5. Profile runA dummy forward pass at maximum batch size measures peak activation memory.
  6. Allocate KV cacheWhatever is left of the reserved memory becomes the KV block pool. The log shows "GPU KV cache size: N tokens" and "Maximum concurrency".
  7. Capture CUDA graphsDecode steps for common batch sizes are recorded once and replayed later with one launch each.
  8. Start HTTPuvicorn starts listening on :8000. /health returns 200.

GPU memory calculator

This is the most important calculation when deploying. Pick a GPU and a model to see how many tokens of KV cache fit.

Estimates. vLLM measures activation memory with its profile run; this calculator assumes about 1.5 GB. The decode floor is weights ÷ memory bandwidth: the fastest a single request can generate tokens.

06 · Engine loop, continuous batching & paged KV

Continuous batching simulator

Six requests arrive at different times. On every engine step, the scheduler fills a token budget: requests already running get 1 decode token each, then waiting requests are admitted with chunks of their prompt (prefill). Each request's KV cache lives in 16-token blocks from a shared pool. When the pool runs out, a request is preempted and later recomputed. Change the settings to see how the schedule changes.

prefill (tokens computed) decode (1 token) waiting in queue running, no budget left preempted ★ first token (TTFT)  ✓ finished

Step 0: what the scheduler did

Token budget used

    KV cache block pool (GPU memory)

    Each square is one 16-token block, colored by the request that owns it. A request's blocks can be anywhere in the pool. Its block table maps logical positions to physical blocks, which is the core idea of PagedAttention. When a request finishes, its blocks go back to the free list.

    What to notice: new requests join while others are mid-generation. That's continuous batching, and there are no batch boundaries. A long prompt (D, 300 tokens) is split across several steps when the budget is small (chunked prefill). Raising the budget lowers TTFT. Shrinking the KV pool forces requests to wait or be preempted.
    07 · Prefill vs decode

    Where TTFT and TPOT come from

    One streaming request

    PrefillDecode
    Workall prompt tokens at once1 token per request per step
    Bottleneckcompute (big matmuls)memory bandwidth (read all weights + KV)
    Shows up asTTFT grows with prompt lengthTPOT ≈ step time

    Why batching is nearly free (toy model)

    Qwen2.5-1.5B on an A10G with 1024 tokens of context per request. Every decode step reads all the weights once, however many requests are in the batch, so adding requests raises total throughput far more than it slows each one.

    step time = max(bytes read ÷ 600 GB/s, FLOPs ÷ ~75 TFLOPS) + ~1.5 ms overhead. These are rough numbers; your benchmark measures the real curve.

    08 · bench.py internals

    How the benchmark measures the server

    The sweep: 3 × 2 × 4 = 24 configurations

    Each cell is one (prompt length, output length) pair, run at every concurrency level. The number of requests per config is max(8, 4 × C). --quick runs only the highlighted cell at C = 1 and 8.

    Three choices that make the numbers trustworthy

    • Random prompts, each starting with a unique hex id. vLLM's prefix cache is on by default, and repeated prompts would skip prefill and make TTFT look too good.
    • ignore_eos=True, a vLLM extension, so every response is exactly output_len tokens. Without it, models stop early and runs aren't comparable.
    • Closed loop: C workers each keep exactly one request in flight, so concurrency is controlled precisely. A 2-request warm-up runs first so the one-time startup costs of the first requests don't skew the results.

    How TTFT is measured

    The timer starts before the HTTP call. TTFT is taken at the first chunk with non-empty delta.content. The first chunk only carries the role, so it's skipped. Token counts come from the final usage chunk (stream_options.include_usage).

    09 · Configuration

    Where vLLM's settings come from

    serve.sh

    CLI flags

    Engine settings. Every flag is listed in vllm serve --help. You can also put them in a YAML file with --config my.yaml (keys are flag names).

    environment

    Env vars

    VLLM_* switches (see vllm/envs.py), plus HF_TOKEN, HF_HOME, CUDA_VISIBLE_DEVICES.

    HF model repo

    Model files

    config.json (architecture), generation_config.json (default sampling settings), tokenizer_config.json (chat template).

    request body

    Per request

    temperature, top_p, max_tokens, stop, and vLLM extras like ignore_eos, min_tokens.

    source

    Config classes

    vllm/config/ (Model, Cache, Scheduler, Parallel…) and vllm/engine/arg_utils.py (turns flags into config objects).

    startup log

    The final config

    At startup vLLM logs the non-default args and the resolved config. It's the easiest place to check what's actually in effect.

    10 · CPU vs GPU

    Decode speed is set by memory bandwidth

    Each decode step reads every weight once. For a single request, the fastest possible decode is therefore about weight bytes ÷ memory bandwidth. Bars show the approximate upper limit for a 7B bf16 model (15 GB) on one request.

    Who does what on a GPU server

    CPUGPU
    HTTP, JSON, SSEmatrix multiplications
    chat template, tokenize / detokenizeattention over paged KV
    scheduler, KV block bookkeepingsampling kernels
    Python orchestration, kernel launchesstoring weights + KV cache

    With small models, the CPU can become the bottleneck. vLLM works around this by running the API server and engine as separate processes and by replaying decode steps from CUDA graphs.

    CPU-only serving

    vLLM has a CPU backend (best on x86 with AVX-512/AMX). You build it from source, set the KV size with VLLM_CPU_KVCACHE_SPACE and pin threads with VLLM_CPU_OMP_THREADS_BIND. It's workable for 1–3B models at low concurrency. For CPU-only production, llama.cpp or Ollama with 4-bit GGUF models are usually faster.

    11 · Runbook

    Commands, in order

    Things to try with your first results

    Cost of prefill

    Compare TTFT at input 128 vs 2048 with C = 1.

    Cost of batching

    Compare TPOT at C = 1 vs 64. It should rise only a little while tok/s rises a lot.

    Saturation point

    Find where tok/s stops rising and waiting becomes greater than 0.

    Check the decode floor

    Is TPOT at C = 1 close to the calculator's decode floor? If it's much higher, overhead is dominating.

    Prefix caching

    Restart with --no-enable-prefix-caching. Results should be unchanged, because the prompts are random.

    Bigger model

    Rerun with MODEL=Qwen/Qwen2.5-7B-Instruct. KV capacity drops to about 1/6.
